## About the Claude Code integration

Claude Code ships with OpenTelemetry instrumentation built in. Set a few environment variables and it exports metrics — token usage, cost, session counts, lines of code, commits — plus structured log events for API requests, tool executions, and permission decisions straight to `https://ingest.telemetry.dev` over OTLP/HTTP. No SDK, no collector, no code changes. With the tracing beta turned on, it also sends a trace for each prompt, with token usage and cost on every model request.

## Key features

- **Zero-code setup:** Telemetry is enabled entirely through environment variables; nothing to install or wrap.
- **Token and cost metrics:** `claude_code.token.usage` and `claude_code.cost.usage` arrive as time series for dashboard inspection and analysis.
- **Traces (beta):** Each prompt arrives as a trace with a span for every model request and tool call, and telemetry.dev adds up the trace's token usage and cost.
- **Session and productivity metrics:** Session counts, active time, lines of code changed, and commits created surface aggregate adoption and productivity trends.
- **Structured events:** Recent API request, tool result, and permission decision records can be inspected individually in the Logs view.
- **Privacy by default:** Prompt, assistant-response, and tool-detail content is redacted by default, with separate controls for each category.

## Get started

1. Create a telemetry.dev project API key.
2. Set the telemetry environment variables in your shell before launching Claude Code:

   ```sh
   export TELEMETRY_DEV_API_KEY="td_live_..."
   export CLAUDE_CODE_ENABLE_TELEMETRY=1
   export OTEL_METRICS_EXPORTER=otlp
   export OTEL_LOGS_EXPORTER=otlp
   export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
   export OTEL_EXPORTER_OTLP_ENDPOINT="https://ingest.telemetry.dev"
   export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer%20$TELEMETRY_DEV_API_KEY"
   export OTEL_RESOURCE_ATTRIBUTES="deployment.environment.name=production"
   ```

   To turn on telemetry for every developer on a team, refer to [Roll out to a team](#roll-out-to-a-team).

3. Run `claude`. Metrics flush every 60 seconds and events every 5 seconds; telemetry.dev shows aggregate metric charts and recent log events that you can inspect individually.

Environment variables must be set before Claude Code starts — exporting them in an already-running session has no effect. For faster feedback while testing, set `OTEL_METRIC_EXPORT_INTERVAL=10000`.

## Add traces (beta)

Claude Code's tracing is a beta and is off by default. To turn it on, set two more variables along with the ones above:

```sh
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
export OTEL_TRACES_EXPORTER=otlp
```

In `managed-settings.json`, add `"CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1"` and `"OTEL_TRACES_EXPORTER": "otlp"` to the `env` object. Traces use the same endpoint and headers as metrics and logs.

Each prompt arrives as a trace that starts with a `claude_code.interaction` span. Under it, each model request has a `claude_code.llm_request` span and each tool call has a `claude_code.tool` span. A subagent's spans sit under the tool call that started it.

telemetry.dev reads the input, output, and prompt-cache tokens on each `claude_code.llm_request` span, along with its time to first token, and calculates the request's cost from the model's standard prices. A request in fast mode, where the span's `speed` attribute is `fast`, costs more than telemetry.dev shows. The trace's usage and cost totals come from these spans. The `claude_code.token.usage` and `claude_code.cost.usage` metrics stay separate charts, so turning on traces doesn't count a request twice.

If your organization also sends [Claude Platform traces](/integrations/claude-platform) to the same telemetry.dev project, each model request also has an API span from Anthropic, under its `claude_code.llm_request` span. telemetry.dev then counts the request's usage once, on the API span. Claude Code adds that link only when it calls the Anthropic API directly. If you go through a proxy set in `ANTHROPIC_BASE_URL`, set `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1` to keep the link; without it, the request counts twice.

## What you can track

Claude Code exports eight metrics and a set of events. telemetry.dev shows each metric series as a chart on the project **Overview** page and each event as a record on the **Logs** page.

| Metric | Unit | Question that it answers |
| --- | --- | --- |
| `claude_code.session.count` | Count | How many sessions do developers start? |
| `claude_code.active_time.total` | Seconds | How much time do developers use Claude Code, without idle time? |
| `claude_code.token.usage` | Tokens | How many input, output, cache-read, and cache-write tokens does each model use? |
| `claude_code.cost.usage` | USD | How much does Claude Code cost, for each model? Claude Code calculates this value. |
| `claude_code.lines_of_code.count` | Count | How many lines of code does Claude Code add and remove? |
| `claude_code.commit.count` | Count | How many git commits does Claude Code make? |
| `claude_code.pull_request.count` | Count | How many pull requests does Claude Code open? |
| `claude_code.code_edit_tool.decision` | Count | How frequently do developers accept or reject the changes of the Edit, Write, and NotebookEdit tools? |

| Event | Claude Code sends it when | Question that it answers |
| --- | --- | --- |
| `claude_code.user_prompt` | A developer submits a prompt | How many prompts does each session send, and how long are they? |
| `claude_code.api_request` | A model request completes | Which model answered, how long did it take, and how many tokens did it use? |
| `claude_code.api_error` | A model request returns an error after its last retry | Which requests do not complete, and with which status code? |
| `claude_code.api_retries_exhausted` | A request stops after more than one attempt | How long do developers wait on retries? |
| `claude_code.api_refusal` | The model refuses a request | How frequently does the model refuse? |
| `claude_code.assistant_response` | A model response contains text | What text did the model return? The text is redacted by default. |
| `claude_code.tool_decision` | A tool permission is accepted or rejected | Which tools do developers permit, and does each decision come from a setting, a hook, or the developer? |
| `claude_code.tool_result` | A tool call completes | Which tools run, how long do they take, and do they complete correctly? |
| `claude_code.subagent_completed` | A subagent returns its result | Which subagent types run, and for how long? |
| `claude_code.skill_activated` | A skill starts | Which skills do developers use? |
| `claude_code.compaction` | A context compaction completes | How frequently do sessions fill the context window? |
| `claude_code.mcp_server_connection` | An MCP server connects, disconnects, or cannot connect | Which MCP servers do not connect? |
| `claude_code.permission_mode_changed` | The permission mode changes | When do developers change the permission mode? |

Claude Code also sends inventory and maintenance events: `managed_settings_resolved`, `plugin_loaded`, `plugin_installed`, `hook_registered`, `hook_execution_start`, `hook_execution_complete`, `hook_plugin_metrics`, `at_mention`, `auth`, `internal_error`, `feedback_survey`, and `retention_sweep`. Each name starts with `claude_code.`. For the attributes of each event, refer to the [Claude Code monitoring reference](https://code.claude.com/docs/en/monitoring-usage).

## Roll out to a team

A managed settings file turns on telemetry for every developer on a machine. Claude Code applies managed settings above the settings of each developer.

1. Write a `managed-settings.json` file. Use literal values, because Claude Code does not expand references between entries in the `env` object:

   ```json
   {
     "env": {
       "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
       "OTEL_METRICS_EXPORTER": "otlp",
       "OTEL_LOGS_EXPORTER": "otlp",
       "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
       "OTEL_EXPORTER_OTLP_ENDPOINT": "https://ingest.telemetry.dev",
       "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer%20td_live_...",
       "OTEL_RESOURCE_ATTRIBUTES": "deployment.environment.name=production,team.id=platform"
     }
   }
   ```

2. Put the file in the system directory of each operating system:

   | Operating system | Path |
   | --- | --- |
   | macOS | `/Library/Application Support/ClaudeCode/managed-settings.json` |
   | Linux and WSL | `/etc/claude-code/managed-settings.json` |
   | Windows | `C:\Program Files\ClaudeCode\managed-settings.json` |

3. On one machine, run `/status` in Claude Code. Make sure that the `Setting sources` line shows `Enterprise managed settings (file)`.

You can also send the same `env` keys through an MDM profile or through server-managed settings in the Claude admin console. Refer to the [Claude Code managed settings guide](https://code.claude.com/docs/en/managed-settings) for each delivery method.

When managed settings set `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_HEADERS`, Claude Code removes the conflicting endpoint and credential variables that a developer sets. As a result, a developer cannot send this telemetry to a different collector. The exporter variables, such as `OTEL_METRICS_EXPORTER`, follow the usual precedence, so keep them in the managed file. Otherwise, a developer can turn off a signal.

Claude Code ignores these OpenTelemetry variables in the `.claude/settings.json` and `.claude/settings.local.json` files of a repository. A repository cannot turn on telemetry or change its destination.

Use `OTEL_RESOURCE_ATTRIBUTES` to tell teams apart, for example with `team.id=platform`. A value must not contain a space. If a value contains a space, Claude Code drops all the keys and shows no error.

### Attributes on each record

Each metric data point and event carries these attributes when they are available:

| Attribute | Value |
| --- | --- |
| `user.email` | The email address of the Claude account that the developer signs in with |
| `user.account_uuid`, `user.account_id` | The Claude account |
| `organization.id` | The Claude organization |
| `user.id` | An anonymous identifier for each installation of Claude Code |
| `session.id` | The Claude Code session |
| `terminal.type` | The terminal, for example `iTerm.app` or `vscode` |
| Keys from `OTEL_RESOURCE_ATTRIBUTES` | The keys that you set, for example `team.id` |

Events also carry `prompt.id`, which connects all the events of one prompt. Metrics do not carry `prompt.id`. To read the attributes of an event, open the event on the **Logs** page and look at the **Data** panel.

## Estimate ingestion units

telemetry.dev counts one ingestion unit for each span, log record, and metric data point. Each event is one log record. We measured the records that Claude Code 2.1.294 and 2.1.301 send:

| Activity | Events | Spans, with traces on |
| --- | --- | --- |
| Session start | 1 or 2, plus 1 for each plugin, hook, and MCP server | 0 |
| Prompt | 1 | 1 |
| Model request | 1, or 2 when the response contains text | 1 |
| Tool call | 2 | 3 |

The first prompt of an interactive session also makes one short model request for the session title. A slash command, such as `/exit`, also counts as a prompt.

Claude Code exports metrics every 60 seconds with delta temporality. An export contains only the series that changed. A minute with model requests sends 5 or more data points: four token types and one cost value for each model, plus active time and code edit counts. A minute without activity sends no data points.

### Example for one developer

This example workload is an assumption. Your numbers can be different. The developer works 21 days a month. Each day, the developer starts 4 sessions and sends 25 prompts. Each prompt makes 8 model requests and 10 tool calls. Claude Code calls a model during 120 minutes of the day.

| Source | Units a day |
| --- | ---: |
| Session starts: 4 × (15 events + 1 data point) | 64 |
| Prompts: 25 × 1 event | 25 |
| Model requests: 200 × 2 events | 400 |
| Tool calls: 250 × 2 events | 500 |
| Metrics: 120 minutes × 8 data points | 960 |
| **Total for metrics and events** | **1,949** |
| Traces: 25 + 200 + (250 × 3) spans | 975 |
| **Total with traces** | **2,924** |

For 21 days, this developer uses approximately 41,000 units a month for metrics and events, or 61,000 units with traces.

A developer who only sends telemetry does not use a seat. Seats are for the members who open telemetry.dev. For the price and limits of each plan, refer to [telemetry.dev/pricing](https://telemetry.dev/pricing).

To use fewer units, keep traces off, or set `OTEL_METRIC_EXPORT_INTERVAL` to a longer interval, for example `300000` for 5 minutes. Each export sends one data point for each changed series, so fewer exports send fewer data points. To see the real count, open **Organization settings → Usage**.

## Good to know

`OTEL_LOG_USER_PROMPTS=1` includes prompt content and also enables assistant-response content unless you explicitly set `OTEL_LOG_ASSISTANT_RESPONSES=0`. Tool parameters and input arguments have a separate opt-in, `OTEL_LOG_TOOL_DETAILS=1`. With these content flags disabled, Claude Code still exports operational metadata including prompt lengths, tool names and outcomes, permission decisions, and session and user identity attributes. Apply filtering or redaction in your telemetry pipeline if those fields are sensitive in your environment.

With tracing on, the same flags apply to spans. `OTEL_LOG_USER_PROMPTS=1` puts the prompt text on the `claude_code.interaction` span, and `OTEL_LOG_TOOL_DETAILS=1` adds file paths and Bash commands to tool spans. A third flag, `OTEL_LOG_TOOL_CONTENT=1`, adds file contents and command output to tool spans.
