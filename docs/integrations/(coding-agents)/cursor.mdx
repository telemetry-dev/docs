`@telemetry-dev/cursor` traces Cursor's agent through [Cursor hooks](https://cursor.com/docs/hooks). You install a small CLI, it adds hooks to your user-level Cursor settings, and each agent turn appears in telemetry.dev as a span with its tool calls and subagents. It doesn't change what the agent does.

This integration sends your prompts, the agent's responses and thinking text, tool arguments, and tool results, including file contents and command output. Version 0.1.8 has no setting to turn that off on your machine. Read [What leaves your machine](#what-leaves-your-machine) before you install it.

## Before you start

- Node.js 22 or later.
- A telemetry.dev project and its API key. Keys start with `td_live_`.

## Set up

<Steps>
  <Step title="Install the CLI">

```sh
npm install -g @telemetry-dev/cursor
```

  </Step>

  <Step title="Add the hooks">

```sh
telemetry-dev-cursor install --api-key td_live_...
```

The command does two things:

- Adds a telemetry.dev entry for each hook it uses to `~/.cursor/hooks.json`. It keeps your other hooks and replaces only earlier telemetry.dev entries.
- Saves the API key in `~/.cursor/telemetry-dev.json`, readable only by your user. Cursor started from the macOS Dock doesn't see your shell's environment variables, so the key has to live in a file.

Add `--environment development` to label the data with an environment other than `production`, or `--base-url` to send it somewhere other than `https://ingest.telemetry.dev`.

  </Step>

  <Step title="Restart Cursor">

Cursor loads the new hooks when it restarts.

  </Step>
</Steps>

## Check that data arrives

1. In Cursor, open **Customize** and select the **Hooks** tab. It lists the installed hooks and any errors. The **Hooks** output channel shows each run.
2. Send a prompt to the agent and wait for the turn to finish.
3. Open the [trace explorer](/platform/traces). The turn appears when it ends, because the integration sends a turn's spans after Cursor's `stop` hook.

If the hooks stop working after you change Node.js versions, run `telemetry-dev-cursor install` again. Each hook entry contains the full path of the Node.js binary that ran the install.

## What is recorded

All turns in one Cursor conversation share one trace. Each turn is a span named after the Cursor chat title, or after the first line of the prompt when Cursor has no title yet:

```text
invoke_agent cursor
├── thought
├── execute_tool {toolName}
├── invoke_agent {subagentType}
│   ├── thought
│   └── execute_tool {toolName}
└── chat {model}
```

- The turn span records the prompt, the final assistant text, and how the turn ended (`completed`, `aborted`, or `error`).
- `thought` spans record thinking text and its duration.
- `execute_tool` spans record the tool's arguments, its result, and any error.
- Subagent spans record the subagent's task, summary, and status.
- `chat` spans record the model name and the assistant text.
- `sessionStart`, `sessionEnd`, `afterFileEdit`, `subagentStart`, and `preCompact` become logs.

Every span and log also carries the Cursor conversation and generation IDs, your workspace path, and the email address of your Cursor account.

Cursor hooks don't report token usage or cost, so these traces have neither.

## What leaves your machine

By default the integration sends this content to telemetry.dev:

- Your prompts and the tasks given to subagents.
- The agent's responses and thinking text.
- Tool arguments and tool results, which include file contents, shell commands, and their output.

The SDK settings that control this, `captureInput` and `captureOutput`, are both on. Version 0.1.8 of the CLI has no flag, config key, or environment variable to change them.

These are sent whatever the settings:

- Your Cursor account email, your workspace path, and the paths of files the agent edits.
- The chat title, or the first 60 characters of the prompt, as the turn span's name.
- Conversation, generation, subagent, and tool call IDs; model, tool, and subagent names; statuses, durations, and compaction counts.
- Error messages from Cursor, including the error text of failed tools.

You can stop telemetry.dev from storing prompt and response content: turn off the environment's switch under **Prompt capture** in the project's [privacy settings](/platform/privacy). telemetry.dev then drops recognized content and replaces span names with `[REDACTED]` before storage. The content still leaves your machine, and identifiers, paths, and error text are still stored after built-in redaction.

To stop sending anything, run `telemetry-dev-cursor uninstall` and delete `~/.cursor/telemetry-dev.json`.

## How it runs

Cursor starts a new process for every hook event. The hook command passes the event to a background daemon over a local socket and returns right away. The daemon keeps spans open between events, sends them in batches, and stops after 15 minutes without events.

Hooks fail open: the hook command always returns `{}` with exit code 0, so a telemetry problem never blocks the agent. Starting the daemon on the first event can add up to 10 seconds to that hook.

## Configuration

Environment variables take precedence over `~/.cursor/telemetry-dev.json`:

| Variable | File key | Default | Description |
| --- | --- | --- | --- |
| `TELEMETRY_DEV_API_KEY` | `apiKey` | None | Ingest API key. Without one, the integration sends nothing. |
| `TELEMETRY_DEV_BASE_URL` | `baseUrl` | `https://ingest.telemetry.dev` | OTLP ingest base URL. |
| `TELEMETRY_DEV_ENVIRONMENT` | `environment` | `production` | Environment on traces and logs. |
| `OTEL_SERVICE_NAME` | `serviceName` | `cursor` | OpenTelemetry service name. |

`install` writes `apiKey`, and `baseUrl` and `environment` when you pass them. If you omit `--api-key`, it reads `TELEMETRY_DEV_API_KEY`. Running `install` again rewrites the file and stops the daemon, so the next hook starts it with the new settings.

To remove the hooks:

```sh
telemetry-dev-cursor uninstall
```

`uninstall` keeps `~/.cursor/telemetry-dev.json`. Delete that file to remove the saved API key.

## Limitations

- **Windows machines shared with other users:** on Windows, the daemon listens on a named pipe whose name is based on your username, and version 0.1.8 doesn't check who created the pipe. Another user signed in to the same machine could create it first and receive your hook events. Don't use 0.1.8 on a Windows machine shared with people who shouldn't see your prompts and code.
- **Agent CLI:** `cursor-agent` sends only some hooks. As of CLI 2026.08 it doesn't send `beforeSubmitPrompt`, `afterAgentResponse`, or `stop`, so CLI traces have tool and thinking spans but no prompt or response text.
- **Cloud agents:** cloud agents run only project hooks from `.cursor/hooks.json` in the repository, not the user-level hooks this installer writes. To trace them, add equivalent project hooks and provide the API key in the cloud environment.
- **Tab:** the integration traces agent sessions, not Tab completions.
- **Subagent parents:** Cursor hook events don't always say which conversation started a subagent. The integration assigns an unknown conversation to the oldest pending Task call, so parents can be wrong when several subagents start at once.
- **Timing:** a `chat` span starts at the end of the previous assistant message, which approximates when the model call began.
